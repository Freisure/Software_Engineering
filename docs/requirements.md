# 需求与验收矩阵

依据用户提供的《软件工程选题.md》实现。项目名“书循环”，定位为同校学生二手教材流转MIS，支持学生与学院管理员两种主角色。

## 1. 范围与原则

核心闭环：发布 → 审核 → 按课程检索 → 预约 → 线下交接 → 双方确认 → 评价与信用。异常通过举报和申诉进入管理员处理队列。在线支付、物流、跨校服务、统一身份认证实际对接不在本期范围。

## 3. 验收场景

| 场景 | 预期 |
|---|---|
| 发布缺图、无效课程或负价格 | 明确拒绝，不能生成有效教材 |
| 待审核/驳回教材 | 不出现在集市；所有者可查看审核说明 |
| 审核通过教材编辑 | 再次进入待审核，不再出现在集市 |
| 两个需求者同时预约 | 一个成功，另一个409冲突，不产生两个有效预约 |
| 需求者接受自己的请求 | 403，只有发布者可以接受 |
| 未开始交接就确认 | 409；合法顺序为接受→开始→双方确认 |
| 单方确认 | 等另一方；超时变为待处理，不自动判另一方爽约 |
| 重复确认或重复裁定 | 不重复增加信用 |
| 举报成立后申诉成立 | 恢复原实际扣分，只能处理一次；不自动恢复已下架信息 |
| CSV第二行无效 | 前面有效行也回滚 |
| 非管理员访问管理API | 403 |
| 修改密码 | 其他会话失效，当前会话继续有效 |

## 4. 明确的产品取舍

- 需求中的“时间段”收敛为一个约定时间点，双方在留言中补充可接受时间范围；不是日历时段资源调度。
- 距离筛选未实现。原稿没有提供校园坐标/校区距离数据，已实现学院与交接地点文本；不采集位置权限。
- 有效预约名额固定为1，未实现候补队列。
- 管理员为全校共享角色，不按学院限制其数据可见范围；学院用于检索和统计筛选。
- 统计时间按教材发布日期，成功交接数按当前完成状态；不是按实际成交日期单独汇总。
- 超时在预约列表访问时处理，或由维护命令周期执行；不含常驻任务服务。
- 基础敏感词与正则脱敏不能取代人工审核，图片中的联系方式需管理员人工识别。
- 举报处罚支持一轮撤销复核；爽约争议可保留证据并进一步联系管理员，本期不实现多级仲裁工作流。

这些边界已在运行说明中说明，不以未实现能力冒充完成项。
